# Verified decision core (epic sommelier-ejb)

`lean/` holds the specification of the engine's decisions in Lean 4 (4.35.0, no Mathlib yet). `cd lean && lake build` checks it.
The model is `lean/Sommelier/Model.lean` (types), the decision function is `lean/Sommelier/Step.lean`
(`step : State -> Event -> State x List Action`, total, computable, axioms: `propext` only), `lean/Sommelier/Safety.lean` holds the safety theorems (ejb.2, below), `lean/Sommelier/Gates.lean` states what each gate DOES to the engine's output (ejb.3), `lean/Sommelier/Truth.lean` states and proves what a reading says about the REAL bar (the verdicts and T1 - T9, below), `lean/Sommelier/Status.lean` defines the status line and the rows as pure functions of `State` and `Read` over those verdicts, `lean/Sommelier/Honesty.lean` proves liveness and honesty about them (ejb.3), `lean/Sommelier/Eqns.lean` generates equation lemmas shared by `Safety.lean` and `Gates.lean` (so `Gates.lean` does not import `Safety.lean`, and a mutant that breaks a `Safety.lean` proof positionally cannot mask a `Gates.lean` theorem; `Honesty.lean` imports `Gates.lean` and `Status.lean`, not `Safety.lean`, so a mutant that breaks a `Gates.lean` proof stops `Honesty.lean` from building and masks every theorem in it), and `lean/Sommelier/Examples.lean` holds
`#eval` examples that are also `decide`-checked, including every counterexample a reviewer found. macOS is an adversary: the safety theorems
quantify over ALL event lists, and `Model.lean` alone never says what a read means; `Truth.lean` says it, from stated assumptions.

**Status (ejb.7).** The Swift app RUNS this model: `LayoutEngine` feeds real reads, user events and actuator results to `DecisionCore.step`, performs the one action it
emits, and shows `statusLine` / `rowLine`. The old Swift order planner, holds, budget, strikes, grants and fold requests are DELETED (`scripts/check-single-decider.sh` keeps them
gone); the "Lean to rule" table below names the Swift mechanism each Lean field replaced, for traceability only. The mapping in
this document is a reading of the former Swift code, to be tested on a device at ejb.8. The theorems are proved about the model. The assumptions they rest on
(A1, A2, A3, A6, A7 and leftmost folding, see `Truth.lean`) are unproved facts about macOS and the adapter, believed from observation: if one is false
on a device, the theorems that use it say nothing about that device.

## Shape (deliberate)

- One decision per read: at most ONE drag leaves per `read` event; the world answers with `moveResult` and the next read decides again.
  EVERY action is one physical drag, for user and engine moves on every bar (retries are later passes). Decided.
- Only a `pass` read that is `settled` and not `incomplete` may plan. A `poll` read, an unsettled read and an `incomplete` read are evidence only
  (evidence rules below apply to all of them).
- A user's pass is the span from a user event to the next `passBoundary`. After `userEdit` (non-empty moved) and `retryKey` only owed keys move; `userRetry` (Re-apply) starts an UNRESTRICTED pass (the engine may move, with one strip grant).
- Owed user moves (the fold request first) are planned before the engine's, never both in one read.
- The planner is a stub (first inversion); `ejb.4` replaces it. The old Swift planner (`Reconciler` order phase) is deleted (ejb.7): this stub is the only order planner.

| `userMove` | `plan(onlyMove:)` + `foldDropRequest`. Exact rule for a drawn owed key `k`: ANCHORS are the movable keys that are in the record, are not `k` and are not still owed (so a key already SERVED is an anchor, and may be a target; a drawn key absent from the record never forces a drag). `k` is RIGHT when the set of anchors before it on the bar equals the set of anchors before it in the record: then no move. Otherwise take the first gap, in DRAWN order of the anchors, whose preceding anchors are exactly that set; the move is `after` the last anchor of the gap, or `before` the first anchor if the gap is empty. If no gap satisfies the test (the anchors are themselves out of record order, or the other keys are owed too) the ANCHOR rule gives no move; it makes no promise that its move improves the order (it is the old rule). There are TWO PHASES in the queue (`userPick`): first every queued key by the anchor rule and the licensed pull-out (the fold request first, then the owed keys; exactly the old behaviour, so `request_first` stands for the pull-out), and only if none yields an allowed move, the FALLBACK in queue order (ejb.10). The fallback applies to an owed, movable, MISPLACED key `k` in the record (some movable record key is before `k` in the record and after it on the bar, or the other way round). It looks at EVERY single drag of `k` (to either side of any movable record key other than `k`) and judges each by its WORST CASE over the possible bars (ejb.11). `freeKeys` are the record keys that could stand anywhere among the open keys of some possible bar: listed by the read (drawn, in the pile, folded or unread), not movable, and not pinned behind a fresh chevron (A2). A record key the read lists nowhere is not on the bar and is never free (`wholeBar_unlisted`: any number of such keys leave `wholeBar` as it is). `wholeBar` is exactly "no free key" (`wholeBar_iff_free`): every listed record key is movable (drawn, trusted, not counted as folded) or listed folded under a FRESH chevron. The worst case of a drag is `worstCount` = the inversions among the movable record keys it leaves (`afterCount`) plus `penalty`, the number of free keys that crossing could cost: moving `k` toward the front (its target stands before it in the drawn order), a free key that comes BEFORE `k` in the record; moving it toward the back, a free key that comes AFTER `k` in the record. (A free key may stand between `k` and its new place on some possible bar; crossing a key on the other side of `k` in the record can only lower the inversions or leave them.) The fallback takes the drag with the lowest `worstCount` (ties to the place just after `k`'s nearest movable record predecessor, else just before its first movable follower) and fires ONLY if that is STRICTLY lower than the inversions of the movable record keys now. It then lowers the record inversions on EVERY possible bar (`fallback_improves_bar`, with no `wholeBar` hypothesis). With no free key `penalty` is 0 and this is the rule of ejb.10. The choice is "lowest worst case", which is what `fallback_best` states: it is not claimed to be the drag that is best on every particular bar. Otherwise there is no drag (the keys around `k` are out of order and no placement of `k` helps; the row says so, see `noMoveHelps`). A no-op never spends the owed attempt or sets a hold. Anchors never move in a restricted pass. A folded key is pulled out only if it is the fold request OR owed, the chevron is fresh and THIS read lists the key as folded (`r.foldedSet`; the pile memory alone never licenses a drag), `after` the rightmost movable key that precedes it in the record. So a drop that macOS folded after the edit (never a fold request) is pulled out on the first good reading. A folded key the user did not drop never gets one. On a usable fresh-chevron read the folded set is the read's own and supersedes the memory (`foldedAll`): a key the memory still lists but this read shows drawn is judged as drawn, for the planner too (it may now plan a key that stale memory used to hide, on the same read the memory is replaced). |
| `engineAllowed` | `gateEngineMoves`: not restricted, no hold, chevron not stale, strip not open, budget left. |

The gdu.144 text "in restricted passes a target-is-moved move needs the pair to have flipped" is replaced by the exact rule above:
a moved key is a valid target once served, and a drawn key is placed by the set test above. The earlier sentence "an already-ordered pair is never moved" is NOT claimed: the guarantee is only that a moved key ends with the right set of anchors before it, anchors stay put, and a no-op drag is never made.

## Assumptions outside the proof (the adapter / actuator must provide)

1. The actuator honours `strip := false`: such a drag never opens the « strip.
2. The actuator answers EVERY action with exactly one `moveResult` (the core never clears `inFlight` otherwise). Theorems about user
   responsiveness take `inFlight = none` as a premise. A result for a drag dispatched before a user event still applies when it arrives
   (a late failed result can re-set the hold after Re-apply; pressing Re-apply again clears it).
3. The adapter sends `passBoundary` at the start of each regular pass and at the end of every user chain, however it ends.
4. The adapter withholds reads during membership (hide/show) batches. Membership actions are outside the core.
5. `posted` is truthful (it comes from `lastMoveTouchedMouse`), and every action runs with `setSingleDrag(true)`.
6. The Re-apply pass does not start with `passBoundary` (that would clear `stripGrant`, which only `userRetry` sets); the adapter sends `passBoundary` for the NEXT regular pass.
   If Swift cannot guarantee this, the grant must be re-derived from `userRetry` by ordering the events in the adapter.
7. ejb.7 needs a separate strip-permission flag in the actuator: `setEngineInitiated(true)` also refuses with the strip open, so it cannot
   express "strip := false" alone.
8. Immovable keys: the adapter leaves them out of `trusted` and out of the `record` it passes; the core has no such concept.
9. Scope of the guarantees: "the engine does not move on its own" is about ORDER drags only. Membership (hide/show) is outside the core and
   proves nothing here.
10. `Read.nearFold` (the churn zone), `trusted`, `kind`, `settled` are supplied by the scanner; they are adversarial inputs.
11. The status line and the rows are modelled as `Status.lean` over the verdicts of `Truth.lean` (below); their TEXT (names, counts, the paused/adoption/order-cap/hand-drag
    contexts, the "Done: X. Next: Y" line, the hand-drag `unreadAfterHandDrag` state and the 60 s position timeout) stays in the Swift adapter. The adapter
    must keep every immovable or uncorroborated key out of `Read.trusted`: order claims are made only about trusted drawn keys (`Read.pinOpen`) and the record.
12. The adapter sends `userEdit` with non-empty `moved`, `userRetry` and `retryKey` ONLY for real user actions. Every budget and strip
    theorem treats these three as the only events that reset the budget or open a user pass.
13. `chevron`, `level`, `pile`, `folded`, `drawn`, `trusted`, `nearFold`, `settled` are scanner inputs (adversarial). "Full bar" means full
    ACCORDING TO THE READS (`fullBar`); the theorems do not know whether the bar really is full.
14. One `State` lives for the app's lifetime. A relaunch is `State.init` again and restarts the budget (3 or 20 automatic moves).

## Open questions, each decided (safer reading chosen)

1. Refused drags. Decided: a drag with `posted = false` is never budget (refund by construction) and EVERY such result, including a
   "verified" one, puts the key in `skipped` (so nothing loops); only a user's `busy` that the CURRENT chain owed is re-armed, once; every other
   user result without a mouse event is consumed.
2. Several failures per key. Decided: on a bar not proven not-full the first failed posted drag gives the key up; once proven, 3 strikes.
3. Hold at launch before any chevron is seen. Decided: a failed posted drag holds whenever the bar is not proven not-full (assumed full counts).
4. `provenNotFull` is revoked only by a chevron (an `incomplete` chevronless read after the proof does not revoke it, as in Swift). So the
   theorem "provenNotFull implies the last three reads were chevronless" is FALSE as written; the true statement is "since the proof no
   read showed a chevron, and three qualifying chevronless reads preceded it". Decided: model unchanged; the true theorem is proved (`proofNeedsThreeConsecutive`).
5. Unsettled complete chevronless reads. Decided: an unsettled complete PASS read neither counts nor resets (Swift ends it before `noteChevronEvidence`); a POLL counts toward the proof whether it is strip-open, unsettled or `exceptSelfPositioning` (Swift `notePollScan`, :1871-1883); `incomplete` resets. The ejb.8 soak must count exactly these reads (A3).
6. Planning on `incomplete` reads. Decided: an incomplete read never plans, and it cannot replace the fresh pile. NOT the Swift behaviour:
   Swift sets `lastFreshChevronObs` whenever a chevron is in the read (`LayoutEngine` ~1691 and ~2596, no level guard) and plans on whatever
   the read holds. Flagged for ejb.5: the adapter must pass incomplete reads as `incomplete`.
7. A user pull-out on a stale chevron. Decided: it waits; the fold request survives until `passBoundary` and is then gone.
8. `userEdit` with empty `moved` changes only the record (as Swift `!movedKeys.isEmpty`).
9. A `moveResult` that does not match `inFlight` is ignored.
10. The bead's `s3_pauseResume` was not found in the repository; `resume` and `resumeUnserved` are reconstructed from the gdu.144 text.
11. The stub planner moves the first out-of-place key before the key in its slot; minimal only by accident.
12. A late failed result after a user event can re-set the hold (assumption 2). Decided: accepted, the user retries again.
13. With the strip open only user moves with `strip := false` proceed (a pull-out waits).
14. `appsChanged`. Decided: dropped; only user events clear given-up keys.
15. Pile union. Decided: only a settled, readable, strip-closed fresh-chevron read replaces `lastFreshPile`; every other read adds to it, so an
    unsettled or strip-open scan can never un-fold a key.

16. `lastDrawn` is set only by reads that may plan (settled pass reads at a non-`incomplete` level), so a partial poll cannot hide the drawn
    keys a drop is judged against. A busy result re-arms the fold request only if the dragged key WAS the request (`flightReq`).

## Decision: Re-apply and the budget promise

Re-apply (`userRetry`) is something the user did, so it resets the budget and grants ONE strip session (`stripGrant`, emitted as a `user := true`,
unbudgeted move). On a full bar one Re-apply may therefore perform 1 granted move plus up to 3 budgeted moves. The product promise reads:
"at most 3 automatic moves between things you do, and pressing Re-apply may also make the one move next to the fold it grants." The model is
NOT changed for this; the theorems count budgeted (`user = false`) drags only.

## Safety theorems (ejb.2, `lean/Sommelier/Safety.lean`)

All quantify over every event list (`run`), so macOS may do anything. "User event" = `isUserEvent` (non-empty `userEdit`, `userRetry`,
`retryKey`; an edit that moved nothing is not one). Method: per-step lemmas by case analysis on `Event`, invariants (`Inv` with a ghost bit
"a user pass is open", `NU` for runs without a user event, `Expired`, `CountInv`) proved preserved by `step`, lifted by induction on the list.
`scripts/check-lean-axioms.sh` fails unless every theorem uses only `propext`, `Classical.choice`, `Quot.sound`.

## Liveness, gates and honesty (ejb.3: `Gates.lean`, `Truth.lean`, `Status.lean`, `Honesty.lean`)

### What a reading says: `Truth.lean` (T1 - T9, no drop memory)

Verdicts are computed from the record and ONE reading (`verdict`, `rowVerdict`); `shownVerdict s r = verdict s.record (s.view r)` is what the window judges (`status_judges_view`).
`s.view r` is the read with the engine's own proof of "not full" in the field, as of BEFORE the read (`view_of_agree`). `State.unmet`, `State.served`, `placed`, `goodRead`,
`ownKeys` and the discharge logic are GONE: a lost drop is no longer remembered, the window says what the latest reading shows (`outOfPlace` / `behindOutOfTurn` for the
key: "not where you put it"; "Try again" is offered). The moves were compared with the pre-deletion step function on 60000 random traces (1.8 million events): same actions, same state in every other field.

### Status and rows (`Status.lean`, `Honesty.lean`)

`statusLine s r`: `moving` when a drag is in flight or the read decides one (and only then: `notStuck`, `notStuck_conv`), else the verdict of the read: `matches`, `matchesExcept U`,
`differs why` (why, in precedence order: `stopped` = the budget is spent, else `barFull` = a hold, else `needsReapply k` = the engine's planned move of `k` needs the strip and no Re-apply granted one (ejb.20, below), else `plain` = "Sommelier has no move to make right now", shown iff nothing is in flight and no move is decided on that read, `plain_is_no_move`; no claim that no move would help), `checking` = cannot tell. `rowLine s r k`: `moving` (the key is in flight or decided), `waiting`
(owed or requested, and the read is not good or a move of the key exists and is blocked; NOT on a good read where the drop needs no move), else `tick` / `behind` / `notWherePut` / `notOnBar` / `cannotTell` from `rowVerdict` alone.

**Needs Re-apply (ejb.20).** `decideMove` withholds an engine move that needs the strip (`needsStrip`: the subject or its target is folded or in the churn zone `nearFold`) unless Re-apply granted a strip session (`stripGrant`), and the planner only ever proposes its first inversion; on a full bar whose first inversion touches the churn zone no engine drag therefore happens. The model keeps that withholding and makes it HONEST (the planner skipping to the next safe inversion stays with ejb.4).
`enginePlan s r` is the engine's planned move on a read (settled pass, good gate, nothing in flight, no queued user move, `engineAllowed`, the planner has a move; judged state as `decideMove`). `withheldStrip s r = some k` iff that move needs the strip, `stripGrant` is false, and `k` is its subject (`withheld_iff`). After Re-apply (`userRetry`) a grant stands, so the status is never `needsReapply` (`needsReapply_after_retry`), and if the planner still has a move on that read it leaves as a granted user move (`reapply_decides`; the planner is re-run on the cleared state, so the same subject is not claimed). Row: `rowReapply s r k` = the status names `k` AND the row mark is "not where you put it" (`rowReapply_true`, `rowReapply_not_tick`: never a tick, never ok). It is not a `rowNote` code: Swift derives it from the status key and the row (`CoreDriver.refreshDisplay`). Swift wording: status "Re-apply to move <name>: the move needs the « strip" (`CoreStatusText.reapplyText`; D7 leaders precede it; never "Menu bar matches"), row note "Re-apply to move this item: the move needs the « strip". Boundary: `Why` encodes `[3, k]` for `needsReapply k` (`decWhy_enc`). Tests: Examples.lean (`nfRead`), `lake exe fuzz` (`reapplyTable`, all 5-key bars with one key near the fold), Oracle `st_d`, mutants `reapply_*` / `rowReapply_*`.

### Trust boundary and port items

The proofs assume (see "Truth statements" below): `Bar.WF`, leftmost folding (T8 only), A1 - A7 and the A3 soak (adapter assumptions: A2 the folded list under a fresh chevron, A3 the three-read proof of "not full"), and that the adapter delivers `passBoundary` and `moveResult`. Nothing else is trusted: the old drop memory is gone.
Port items (the Swift must change; the model is the spec):
1. Replace `statusLine` / `rowState` by the verdict forms above, fed from `shownVerdict` / `rowVerdict`. `Read.notFullProven` is fed from `!fullBarState`, not Swift's `notFullProven`.
2. The pass on which the proof takes effect is one pass LATER than Swift (the fourth chevronless pass read, the model judges a read by the state before it): the port needs a follow-up pass or Moving strands.
3. `stopped` needs nothing pending and a spent budget; Swift also shows it for a held strip move (`gatedDiffers`, LayoutEngine.swift:1982): in the model that is a `differs plain` ("no move to make right now").
4. Every move, the user's drop included, waits for a USABLE reading (D2): a stale chevron, an open strip, an unsettled, incomplete or unobserved read, a poll, or a chevronless read before the proof gives "Checking" and no move.
5. Feed `Read.unread` (apps whose read failed or was skipped, stale off-bar items, parked items with a nil Control Center flag) and subtract the pile keys from `drawn` (A6, A7).

Known limits (stated, not proved away): "matches except U" is not final placement (a tick next to an unread key); "Try again" needs a USABLE read to do anything, so with a stale
chevron it waits (row `waiting`), then the attempt expires at the pass boundary and, while the chevron is still stale, the row reads "can't tell" (`cannotTell`; status "Checking the menu bar"): an unusable read has no `rowVerdict` beyond that. "Not where you put it" appears only once a USABLE read shows the key out of place; a key remembered as folded but absent from the read gets no pull-out;
T9 is one-way and is about the whole read, not a row; `heldStrip` has no reason text; the truth theorems are only as good as A1 - A7 (A3 needs the soak). The positional claims
`drop_expires`, `stopped_true` and `barFull_true` are about the ENGINE: Re-apply (a user event) is outside them.

## Truth statements (ejb.3, `lean/Sommelier/Truth.lean`: T1 - T9 proved, imported by `Sommelier.lean`)

What a reading says about the REAL bar. `verdict rec r` (matches / matches except U / differs / can't tell) and `rowVerdict` are computed from the record and ONE reading; the
theorems T1-T9 tie them, and the engine's moves, to "every bar macOS could honestly have drawn". The assumptions about macOS, in plain language (a reading is USABLE only if it is a
settled, observed pass read of a readable tree, strip closed, with a fresh chevron or the proof that there is none; nothing is believed from an unusable read):

- A1. On a usable read, the trusted drawn keys really are open on the bar, in the order the read shows them.
- A2. On a usable read with a FRESH chevron, the keys the read puts in the pile or folds really are behind the chevron. (Keys that Swift merely INFERS to be folded, `foldedParked`, are
  not measured, so they must go to `unread`; how `foldedParked` is treated is an open question with the user and is not decided here.)

  counts nor resets, as in Swift; an incomplete read or a chevron resets). - A5. A reading describes one instant of the bar; no statement relates two readings (T6/T7/T9 relate a reading to the one move decided on it).

- A6. On a usable read, every key on the bar, open or behind, is drawn, in the pile, folded or `unread`. A key listed nowhere (an app that is not running) is not on the bar. An `unread` key may be anywhere.
  - *Adapter rule for "not on the bar" (ejb.13, `ReadAdapter.decideAbsence`), only two cases.* A record key that is in none of drawn, pile and unread is left out ONLY if (B) the scan itself saw it parked and Control Center reports it hidden, or (i) it is an app key and NO app that could own it is running: its own name, a helper or relative of that name (`related`: equal names, dotted prefixes, long common prefixes such as `...Hazel` / `...HazelHelper`, team-id prefixes), or a Control Center family (`ReadContext.ownerFamilies`), judged from the scanner's `runningApps()` at the start of the scan. EVERYTHING ELSE that is not drawn or pile is `unread`: a `module:` / hosted-only key, an app key whose owner may be running, any key when there is no owner evidence. (An earlier "clean read" rule (ii) and an allow-list of system modules were deleted: the allow-list matched names an app can set itself, and (ii) declared old aliases of visible items "not on the bar".) Only a RECORD key is trusted or pile; the drawn keys of an owner that has a record key forced unread are untrusted. Immovability (every `module:` key is immovable in production) says nothing about identity.
  - *Residual macOS-side assumption (B), to be watched live (ejb.8):* the Control Center flag is authoritative: a parked item that Control Center lists as hidden is not on the bar.
  - *Residual macOS-side assumption (i), to be watched live (ejb.8):* an app's status item exists only while the app or one of its helper processes is running. ## A verified move the next read contradicts is a strike (ejb.17: `lean/Sommelier/Verified.lean`)

The actuator may call a posted drag `verified` while macOS has reverted it, or the drag did not take: the NEXT read still shows the key out of place. Before ejb.17 the core
planned the same drag again on every such read, bounded only by the budget (3 on a full bar, 20 on a bar proven not full) with no per-key limit; the old Swift engine stopped
after 3 (`unverifiedStrikes`, `revertWatch`). The rule now:

* `result` records the subject of a posted ENGINE drag answered `verified` in `State.verified` (`res_verified_marks`); nothing else leaves a mark (`res_unverified_no_mark`).
* The next read that the gate accepts (`State.gate`: usable and consistent) with nothing in flight JUDGES the mark (`judge`, run BEFORE the read decides: `decideMove s r = decideMove0 (judge s r) r`,
  so the repeat is never planned from the read that struck the key). If the key's OWN drag did not take (`verFailed`, ejb.26) it takes a STRIKE; `verFailed` is both (1) `stillMisplaced`
  (movable, in the record, and some movable record key stands on the wrong side of it: `misplaced`) and (2) `revertedFromAnchor`: among the movable keys, the read draws `k` and the
  anchor `rel.target` the drag put it next to (`State.verRel`, recorded by `result`) in the OPPOSITE order to the one the drag made (`k` before its anchor for an `after` drag, behind it for a `before` drag).
  Only the order of those two keys counts, so a record key `y` that macOS moves across `k` (not the anchor) cannot make a strike (`crossing_keeps_verdict`, `crossing_move_keeps_verdict`,
  `judge_landed_no_strike`). If the anchor itself crosses back, the read is indistinguishable from a revert and strikes. An anchor the read does not show movable cannot be judged: no strike.
  The key takes a strike (`markStrike`, the strike of a failed drag on a proven bar: given up at the third) and the mark is cleared
  (`judge_contradicted_strikes`, `judge_contradicted_giveup`); otherwise the mark is just cleared, no strike (`judge_confirmed_clears`). A read that cannot judge (unsettled, strip open, a poll, unusable, a drag in flight)
  leaves the mark (`judge_unusable_keeps`).
* Choice, on a bar NOT proven not full: the contradicted move takes the same strike (no hold, no immediate give-up). A failed posted drag on such a bar holds the bar because a failure says the
  bar's reading is unreliable; a verified drag the read contradicts says only that this key did not move, so the key's three strikes (which agree with the full bar's budget of 3) are the limit and
  the rest of the bar keeps working.
* ANY record change clears the mark (ejb.26): `userEdit` clears `verified` whether or not it moves a key (`edit_clears_verified`), because the record the drag was judged against is gone; the read after an edit
  takes no strike (`edit_read_no_strike`, `verified_drag_edit_read_no_strike`: after a verified drag of `k`, an edit and a read, `k` has no more strikes than before the drag). A `userEdit` that moves no key
  still does not clear the strikes or the budget (only the mark): a user edit can thus make a pending drag go unjudged, which is accepted (a user action). `userRetry` clears all (`retry_clears_verified`), `retryKey` that key (`rk_clears_verified`).
  Given-up keys are skipped by the planner, so a stuck key stops the whole order phase until the user acts (as a failed key always did).

Headline: `verified_revert_bounded`: from `State.init rec`, over any event list with no user event and no edit at all (`vFree`: ejb.26 hypothesis change, `isUserEvent` does not count an edit that moves no key, but such an edit now clears the mark and
so could dodge a strike), in which every drag of `k` is answered `verified` (posted) (`AllVerified k es`) and every read the gate accepts while a drag of `k` awaits judgement shows it undone, `k` still misplaced AND on the wrong side of its
anchor (`AtReads (StillMisplacedAtGate k)`: macOS reverts `k` every time), `verDrags k (State.init rec) es <= 3`: at most three posted engine
drags of `k`, on a full bar and on a proven one alike, whatever the hold, the pile or the other keys do. `verified_revert_bounded_from` states it from any state satisfying `VInv` as
`<= 3 - strikes of k`. Proof: a potential `pot k s` (none once `k` is given up; else 3 less its strikes, less 1 while its verified drag awaits judgement) never rises (`pot_step`, `pot_judge`) and
each posted drag of `k` lowers it by one (`verDrags_le_pot`); the invariant `VInv` (a mark exists only with nothing in flight; three strikes imply given up; an engine drag in flight is not of a given-up key)
is preserved by every non-user event (`vinv_step`). `lake exe fuzz` checks it on random bars that macOS never changes (`revert_bound`, `revert_struck_at_three`, `revert_hit3`) and the two no-false-strike cases on random bars (`honest_no_strike`, `honest_mark_cleared`, `edit_no_strike`, `crossing_no_strike`); examples `editAfterVerified`, `crossedAfterVerified` are also fixtures; `mutants.py` has the `ver_*` mutants.
The Swift suite: `RecordOrderEngineTests.aVerifiedMoveThatTheReadStillPlansIsStruckNotRepeated` (3 drags, plain config), `...OnABarAssumedFull`, `aKeyMacOSKeepsRevertingIsDraggedAtMostThreeTimesNoMatterHowManyPassesRun`.
(The R1 review caveat of ejb.15, "the core repeats a verified-but-undone drag until its budget", no longer holds.)

## Where a drop gets no move

What is true now (ejb.11). The fallback is judged by its WORST CASE over the possible bars (see the `userMove` row): it fires only when its drag strictly lowers the record inversions on EVERY bar the read could have been taken of, whether or not the read verifies the whole bar (`fallback_improves_bar`). A drawn record key that is untrusted, an unread record key, or a pile/folded record key under a chevron that is not fresh is FREE: it can stand anywhere among the open keys, so a drag is only taken when it cannot cost an inversion across such a key. Where no drag qualifies and the read does not verify the whole bar the row says "Sommelier can't yet see enough of the bar to place this item" (`cantJudge`), which claims no more than that. The queue has TWO PHASES: every queued key by the anchor rule (the old rule, no promise that its move improves the order) and the licensed pull-out first; only if none of them moves, the FALLBACK for an owed misplaced key. `drop_mutual_inversion`, `drop_no_gap`, `drop_no_gap_note` and `drop_keys_around_say_so` (Honesty.lean, `by decide` on the exact traces) pin the cases.

- (b) Mutual inversion, answered. Record [1,2,3], the user drops [1,2] (both owed), the bar draws [2,1,3] (1 inversion). Neither key has an anchor move; the fallback moves 1 `before` 2 (0 inversions). Once verified, key 1 is an anchor and key 2 is right. Each key dropped alone also moves (1 `before` 2; 2 `after` 1).
- (c) No gap. Record [1,2,4,3], bar [2,3,4,1] (4 inversions). Dropping 1, 3 or 4 gives a move (1 `before` 2, 3 `after` 1, 4 `after` 2). Dropping 2 gives NO move: no single drag of 2 leaves fewer than 4 inversions (the earlier rule dragged it to the end, 5 inversions, worse), and its row carries `noMoveHelps` ("No single move of this item would improve the order"). A press of "Try again" shows the same.
- (a) Vacuous tick, UNCHANGED and approved. Record [1,3], the user drops 3, the read draws [3,1] with only 3 trusted. Key 1 is not pinned, so 3 has no anchor to be out of order against: no move, row 3 ticks, status "matches except 1".

Single-drop table (fresh chevron, every drawn permutation, every dropped key, EVERY KEY TRUSTED; from `lake exe fuzz`): 4 keys: fallback fires 20, worse 0, unchanged 0; anchor rule fires 48, worse 0, unchanged 0; no move 28. 5 keys: fallback 196 / 0 / 0; anchor rule 256 / 0 / 0; no move 148. Multi-drop (every permutation and nonempty dropped subset, drained with verified drags, EVERY KEY TRUSTED): ends with MORE inversions than it began in 0 of 360 (4 keys) and 0 of 3720 (5 keys) cases. These are counted by the fuzz harness and the oracle, not theorems. The "0 of 360" assumes every key is trusted; it does not hold in general, because the anchor rule is old behaviour (pre-existing, ejb.3) and carries no improvement theorem: it can still make the order worse on a multi-drop and on "Try again". Traces (record [1,2,3,4], bar [2,3,4,1], 3 inversions): (i) the user drops 2, 3 and 4 and keys 3 and 4 are untrusted (the engine cannot place them): the anchor rule moves 2 `after` 1 (`[3,4,1,2]`, 4 inversions) and nothing else is movable, so the drain ends worse; (ii) the user drops 3 and 4, then presses "Try again" on key 2: the anchor rule moves 2 `after` 1, again 4 inversions (`retryKey 2` after `userEdit [1,2,3,4] [3,4]`, read `[2,3,4,1]`). The fallback never makes such a move (it is judged by `fallback_improves_bar`), and only the fallback is claimed to improve.

ejb.11 numbers (`lake exe oracle`, every key status: trusted drawn, untrusted drawn, pile, unread, listed nowhere; fresh chevron and none; every dropped subset; the semantic ground truth is every possible bar over the keys and the pile key): 4 keys exhaustive (50670 cases) and 5 keys sampled (3317 cases). The row says `cantJudge` in 552 of the 4-key cases (it was 5136 before ejb.11) and in none of them does a drag next to a movable record key lower the inversions on every possible bar (it was 2972 of 5136, i.e. `cantJudge` hid an improving drag more than half the time). The fallback is checked on every possible bar of every case in which it fires (140590 bar checks): never needless, never worse, always strictly better (0 failures). In each of the 685 `cantJudge` cases enumerated (552 + 133 five-key) some drag, to some place in some possible bar, does improve that bar, which is why `noMoveHelps` is not claimed there.

What still gets no move, and where the screen says so (`owed_unanswered_reason`, `userMove_none_reason`, `rowNote_true`, `rowNote_reason`, `noMoveHelps_true`):

| reason | on screen |
|---|---|

`try_again_answers` ties these together for "Try again" (`retryKey`); `userRetry_answers` does the same for Re-apply with the status line (`differs plain`, "Sommelier has no move to make right now", shown iff no move is decided on that read). Nothing here claims that the engine will correct the other keys. Exhaustive checks: `lake exe fuzz` (`drop_answered_if_reducible`: when one drag of an owed key lowers the inversions, something leaves; `drain_bound`; `note_true`; `fallback_reduces`; `fallback_bar_improves` on the honest random bars) and the semantic oracle `lake exe oracle [n]` (lean/Oracle.lean, exit code 1 iff any check fails; it enumerates every honest bar over four keys and checks the status, the rows, the moves, the notes and the drain against them, with the ejb.11 `S_*` checks (`statusOracle`: `S_fallback_not_worse`, `S_fallback_strict`, `S_cant_hides_safe_drag_*`, `S_helps_true_on_every_bar`, `S_drain_*`) and `F_answered`, `F_fallback_best`, `F_helps_true`, `F_try_again`, `F_retry_answers`, `F_drain_*`, and, for 4 and 5 keys over every drawn set, order and trusted subset, `W_fallback_bar_improves` (a fallback move strictly lowers the record inversions on every possible bar), `W_helps_bar` (a `noMoveHelps` key has no better place on any possible bar) and `W_cant_unverified`; the old `W_fallback_whole` is gone: the fallback no longer needs a verified bar).

Liveness still rests on the adapter delivering `moveResult` and `passBoundary`. The queue does not "empty" by moves alone: a key that needs no move stays owed, with its reason above, until the boundary.

## How the app runs the proved code (ejb.5)

The app does not port the Lean model to Swift. The Swift module `DecisionCore` (`Sources/DecisionCore/`) links the C that Lean itself generates from the proved
definitions and calls it. `SommelierCore` does not use it yet (wiring is ejb.7).

### The boundary

```
Swift value types (Key, Read, Event, Action, Rel, Status, Row, RowVerdict, Verdict)
   | Codec.swift: flat UInt32 words (length-prefixed key lists)
   v
lean/shim/sommelier_lean.c      C: UInt32 words <-> Lean Array Nat, runtime and thread init, refcounts, malloc'd answer
   v
lean/Sommelier/Ffi.lean         @[export]: decode, call the PROVED function, encode
   v
step, statusLine, rowLine, rowNote, shownVerdict, rowVerdict   (Step.lean, Truth.lean, Status.lean: unchanged)
```

Exports (`sommelier_init/step/status/shown_verdict/row_line/row_verdict/row_note/adopt/gesture/describe_event`) are thin: each is `decode; call; encode` and nothing else (`…Tok` functions in `Ffi.lean`).
An answer is `0 :: payload`, or the single word `[1]` when the INPUT does not decode (`step` then also returns the state unchanged). There is no default value for
a malformed event, read or key: Swift throws `DecisionError.malformedInput`. `ok_ne_err` proves the two answers cannot be confused.

States are immutable and persistent: `DecisionCore.step` returns a NEW `DecisionState` and leaves its input usable. The C handle is released in `deinit`.

**Row notes (ejb.14).** `sommelier_row_note(state, read, key)` answers `0 :: [code]` with the code of `rowNote s r k` (`DecisionCore.rowNote(state, read, key) -> RowNote?`, `nil` = no note; a malformed read or key throws `.malformedInput`, a word that is no note code throws `.undecodableOutput`). It is thin like the others and runs `rowNoteF` (`Fast.lean`), which differs from `rowNote` only by calling `rowLineF`, `fallbackMoveF`, `userPickF` and `decideMoveF`; `rowNoteF_eq` and `rowNoteTokF_eq` prove it equal to the specification with no hypothesis. The fixture prints each probed row's note by name (`none`, `noMoveHelps`, `cantJudge`, `noMoveHere`), the named traces `note-noMoveHelps`, `note-cantJudge-T1`, `note-cantJudge-T2` (review-10b) and `note-none-moving` cover the cases, and the 2000 fuzz traces show all three notes; `fastfuzz` compares `rowNoteF` with `rowNote`.

### Use the bar's current order (ejb.9: `lean/Sommelier/Adopt.lean`, `sommelier_adopt`, `CoreAdoption`)

The Arrange button "Use the bar's current order..." saves the bar as the record, with no drag. The decision is Lean's: `adoptProposal s r` answers `some L` only when `shownVerdict s r = differs` (which already means the view `s.view r` is usable and consistent, `differs_usable`), and `L = adoptRecord s.record (s.view r)`; otherwise `none` (`adoptProposal_none`, `adoptProposal_iff`).

**The rule (slots).** The record keys the read PINS are its on-bar keys: the pile and folded keys of a usable fresh-chevron read (`pinBehind`, each once) and the trusted drawn keys (`pinOpen`). Their order becomes the read's: behind « first, then the open keys left to right (`adoptSeq`). Every other record key (not running, unread, drawn but not trusted, not listed) keeps its exact SLOT: the positions of the on-bar keys are refilled, in the record's slot order, with the on-bar keys in the read's order (`fillSlots`). So off-bar keys never move (their relative order and their places are kept), nothing is gained or lost, and a record that already agrees is returned unchanged. A read that pins nothing (not usable) returns the record unchanged (`adoptRecord_unusable`). Untrusted and unread keys are left where they are on purpose: the read cannot say where they stand.

**Proved** (standard axioms only, in `scripts/check-lean-axioms.sh`): `adoptRecord_perm`, `adoptRecord_mem`, `adoptRecord_nodup` (a permutation of the record: no key gained or lost, no duplicate); `adoptRecord_offbar` (off-bar keys keep their order) and `adoptRecord_onbar` (the on-bar keys are `adoptSeq`); `adoptRecord_okL` (the pinned keys alone agree with the adopted record), hence `adoptRecord_not_differs` (`forcedBad = false`), `adoptRecord_matches_pinned` (`barMatches (adoptRecord rec r) <pinOpen, dd pinBehind>`: the bar the read pins, i.e. the bar if nothing else is on it, matches), `adoptRecord_verdict` (the exact verdict: `cannotTell` if two or more free keys clash only with each other, else `matches` if no free listed key can clash, else `matchesExcept U` for those unread/untrusted keys) and `adoptRecord_verdict_ne_differs`; `adoptRecord_matches_of_no_free`: when no record key is a free listed key, the verdict is `matches` and EVERY bar the read allows matches the adopted record. `adoptProposal_spec` bundles the contract of the button. What is NOT claimed: when some record keys are unread, the next reading says `matches except` those keys, never plain `matches`, because an unread key may stand anywhere; the real bar's reading (`Fixtures/realbar.json`) gives `matches except` its five unread keys.

**Boundary.** `sommelier_adopt(state, read)` answers `0 :: [0]` (no proposal) or `0 :: 1 :: record` (`encAdopt`/`decAdopt`, round trip `decAdopt_enc`; wrappers `adoptTok_enc`, `adoptTok_bad`). It is thin like the others and calls the specification `adoptProposal` (O(n^2), no fast twin needed at n ~ 50). Swift: `DecisionCore.adoptProposal(state, read) -> [Key]?`.

**Swift** (`CoreAdoption.swift`). `CoreAdoption.proposal(state:read:keys:)` and `proposal(record:read:keys:)` return the proposal as engine keys. The engine asks it of the same `(state, read)` pair as the status and publishes it in `CoreDisplay.adoption` (nil unless the core says differs). `CoreAdoption.preview(proposal:layout:)` re-slots the proposal into `Layout.visible` (keys of Visible that are not in the core's record, such as the chevron or immovable items, keep their places; a proposal naming a key that left Visible, or changing nothing, gives no preview) and lists the keys whose position changes. The Arrange button is enabled only with a preview; it opens a sheet listing the changes with Save / Cancel; Save is `setLayout(layout, basedOn:, moved: [])`, an ordinary user edit that owes no drag. Tests (`CoreAdoptionTests`): the real scanner types into the export, the real bar, and the engine: after Save the next passes make zero actuator calls and the status is `matches`. The live use on a real bar is by the user's request only, with a backup of `layout.json`.

### Gestures (ejb.32: `lean/Sommelier/GestureDef.lean`, `Gesture.lean`, `GestureProv.lean`, `sommelier_gesture`, `Layout.applying`)

**Why.** On 2026-11-10 one Arrange drop of one item was turned by Swift code into "the user moved nine items" (gdu.149), and the proved core faithfully made four drags: the proof trusted an input nobody had proved. Since ejb.32 the step from a drop to the new layout and to "what the user moved" is computed by proved code: a drop is an INPUT (`Gesture`), `applyGesture unit sys L g : Layout3 x List Key` returns the new three-section layout and the moved keys.

**Model.** `Layout3` (visible, hidden, alwaysHidden), `unit : Key -> Nat` (the hide unit, data), `sys : Key -> Bool` (the trailing system-module keys, data), `Gesture.drop k section index?` (a Move left/right is a drop with the computed index) and `Gesture.hideNotFitting ks`. Semantics = the Swift semantics of gdu.149 (`moveKey`, `hideStep`): a drop into the section the key already sits in lifts only that key and re-inserts it at the clamped index (the index is taken after the lift); a drop into another section (or of a key the layout does not list) moves the key's whole unit, the key at the index and its siblings right behind it in their previous layout order; no index appends, except in Visible, where it inserts before the trailing system run; a drop reports `moved = [k]`; hide-what-does-not-fit moves each Visible named key with its unit to the end of Hidden and reports every key it moved, once each.

**Proved** (standard axioms only; `Pins.lean` pins the statements; `scripts/check-lean-axioms.sh` lists them):
- G1 same-section drop: `same_perm` (permutation), `same_section` (every key but `k` keeps its section), `same_order` (the section without `k` is the old section without `k`: the relative order of all other keys is unchanged), `same_other`, `same_idx` (`k` lands at the clamped index), `drop_moved` (`moved = [k]`).
- G2 cross-section drop: `cross_unit_in` (every key of `k`'s unit in the layout, and `k`, is in the target section), `cross_group` (those keys are exactly `k :: siblings`, the siblings in their previous layout order, in the target section), `cross_group_ne` (none stays elsewhere), `cross_section` + `cross_order` (every key outside the unit keeps its section and its relative order with every other non-unit key), `cross_idx`, `drop_moved`.
- G3 `gesture_nodup`, `gesture_mem`: no gesture duplicates or loses a key (the keys afterwards are the layout's keys and, for a drop, the dropped key).
- G4 `hide_spec`: in a duplicate-free layout whose hide units are all-or-nothing (`UnitNormal`, what `normalizedHideUnits` guarantees): a key outside the named keys' units keeps its section, the relative order of everything else is unchanged, Hidden/Always hidden keys stay where they are and a Visible key stays Visible or goes to Hidden (the only change of section is Visible to Hidden); the moved keys are listed once each and are layout keys.
- G5 provenance (`GestureProv.lean`, composed with `step`): `userEdit_provenance` / `gesture_provenance` / `drop_provenance`. From ANY state `s`, after `step s (.userEdit rec moved)` with `(L', moved) = applyGesture ...` and `rec = coreRecord mov L'` (the Visible keys the core takes as the record: movable, each once), every action with `user = true` on the reads that follow, until the next user event (`isUserEvent`), has its subject in `moved` OR in `s.owedKeys` OR it is `s.foldRequest` OR the subject of the drag already in flight in `s` OR it is the one strip move a Re-apply granted (`a.strip = true` and `s.stripGrant = true`). It uses the existing single-step theorem `userLabelHonest` (Safety.lean) and proves by induction over the run (`run_provenance`, invariant `ProvInv`; `provInv_step`, `provInv_result`, `provInv_emit`) that no event but a user event puts a new key into that set. `drop_provenance_idle`: from a quiescent core (nothing owed, requested, in flight or granted) the ONLY user-flagged drag after a drop of `k` is a drag of `k`. Keys owed BEFORE the drop stay owed: `step` keeps `owedKeys` through a `userEdit`, so the bound is stated with them.
No Fast twin: one call per gesture, never on a hot path (`stepF` etc. exist for the per-read paths only).

**One corner of the Swift semantics, stated.** `Layout.move` of a Visible key into Hidden also lifts a unit sibling that sits in Hidden/Always hidden (a unit split across sections) and re-appends it to Hidden (an Always hidden sibling thus changes section). The theorem G4 therefore assumes `UnitNormal`; a split unit never survives `normalizedHideUnits`, which `setLayout` and `Layout.validated` apply, so the corner is unreachable from the Arrange window. It is kept as it was (the differential test covers split units against the old Swift code) and not changed silently.

**Boundary.** `sommelier_gesture(layout, units, sys, gesture)` (no state): layout = three length-prefixed key lists; units = length-prefixed `(key, unit)` pairs flattened (a key not listed is its own unit: `4294967296 + key`); sys = length-prefixed key list; gesture = `[0, k, section, 0]` | `[0, k, section, 1, index]` | `[1, n, keys...]`. The answer is `0 :: layout ++ length-prefixed moved`, or `[1]` if ANY input does not decode. Round trips: `decLayout3_enc`, `decGestureResult_enc`, `decUnits_enc`, `decKeyList_enc`, `decGesture_enc`, `decSection_enc`; wrappers `gestureTok_enc` and `gestureTok_bad_layout/units/sys/gesture`; `decGesture_malformed`, `decGestureInputs_malformed`. Swift: `DecisionCore.applyGesture(layout:units:immovable:gesture:)` and, in `SommelierCore`, `Layout.applying(_:units:)` (`GestureCore.swift`), which `Layout.move`, `Layout.hideNotFitting`, `ArrangeDrop.outcome / drop / step / hideNotFitting` and the System Settings adoption call. A `DecisionError` refuses the gesture with a visible message ("Sommelier's layout core could not compute this change ... nothing was changed."); there is no fallback to Swift logic. The pre-ejb.32 pure-Swift implementation lives ONLY in `Tests/SommelierCoreTests/GestureOracle.swift`.

**Tests and checks.** `GestureExamples.lean` (concrete layouts incl. the nine-key unit, imports the definitions only); the gesture fuzz (`GestureFuzz.lean`, run by `lake exe fuzz`: 6000 random layouts/drops/hides against an independent statement of the meaning, tables `gesture_*`); mutants `gest_*` (12; killed by the examples/fuzz by meaning, the one semantically equivalent mutant by a proof); `GestureTests` (Lean's fixture, printed by NAME: 11 named + 1500 random gesture cases, malformed inputs); `GestureDifferentialTests` (6000 drops + 3000 hides + 500 Arrange hides, Lean vs the old Swift code, layout and moved identical, split units and duplicates included); `Gdu149Tests` and the reviewer's suites `RvIncident149`, `RvProp149`, `RvProp149b` through the Lean path.

**The trust boundary that REMAINS (said plainly).** (1) UI row -> section index: which gap of the displayed strip the user dropped into, and `ArrangeDrop.index` / `clamp` turning it into an index (Swift; covered by tests, not proved). (2) `ItemKey` identity and the `ItemKey <-> core Key` scratch table: that two `ItemKey`s that mean the same menu bar item are equal, and which unit a key has (`HideUnitRule`, the tracked-entry resolver). (3) The scanner: what is on the bar, which keys are movable (`Capability`), which are system modules. (4) What happens to the layout between the gesture and the core: `setLayout` merges engine additions, normalizes hide units, applies the pending-adoption drop (`applyingDrop`) and `effectiveUserMoved` filters the named keys (it can only shrink the set, so G5's bound still holds; it is not itself proved), then `coreUserEdit` builds the record (`coreRecordIDs`). (5) Capability refusals, the "will not fit" hint and the no-op test in `ArrangeDrop.outcome`. None of these can make the core owe a drag of an item the gesture did not name, but a wrong index, a wrong unit table or a wrong key identity would put the right item in the wrong place.

### Threading rules

* The Lean runtime is initialised exactly once per process (`pthread_once` in the shim), by whichever call comes first. Nothing to call.
* Every other thread that calls in is initialised on its first call (`lean_initialize_thread`) and finalised at thread exit (a pthread key destructor). Callers do nothing; this works from GCD, `Thread` and the Swift concurrency pool (tested).
* Every state is marked multithreaded (`lean_mark_mt`) at creation, so reference counts are atomic: one `DecisionState` may be read, stepped and released from any threads at once (tested: four readers and two steppers on one state, release on another thread).
* `step` never mutates its input. Two threads stepping the same state each get their own result; keeping ONE ordered "current" state is the caller's job (ejb.7: a single serial owner).
* No locks and no globals in `DecisionCore`; it does no I/O, clock, AX or logging (a test greps the sources).

### Cost

Measured at 36 record keys and 36 drawn keys (native Lean, `IO.monoNanosNow`): `step` averages 16 us. The worst case is 22 to 45 ms, always a read that gives an owed, misplaced, drawn key its FALLBACK move.
Cause: `fallbackMove` takes `argmin (worstCount s r k)` over the `2n - 1` candidate drags (71 at 36 keys). `argmin` recomputes `f` at each step (once for the candidate, once for the current best), so `worstCount` runs about twice per candidate. One `worstCount` (it applies the move to the drawn list and counts inversions) measured 153 us at 36 keys: 71 x 153 us = 10.9 ms for one pass, and the whole call measured 21.9 ms.
`rowLine` (average 456 us over random probes, 26 ms worst) runs the same code: `waitingKey` calls `userMove`, and `userPick` calls `fallbackMove` (380 us of the average); `rowVerdict` adds about 100 us at 36 keys.
The paragraph above is the cost of the SPECIFICATION (`step`, `rowLine`, ... in `Step.lean`, `Truth.lean`, `Status.lean`, unchanged). The exports run the FAST versions of `lean/Sommelier/Fast.lean` (ejb.12), each PROVED EQUAL to the specification for all states and reads, with no hypothesis on the inputs: `fallbackMoveF_eq`, `gateF_eq`, `verdictF_eq`, `rowVerdictF_eq`, `userMoveF_eq`, `userPickF_eq`, `decideMoveF_eq`, `stepF_eq`, `statusLineF_eq`, `rowLineF_eq`, and in `Ffi.lean` `stepTokF_eq` & co. (all in `scripts/check-lean-axioms.sh`, standard axioms only). I chose proved-equal functions plus re-pointing the `@[export]` wrappers to them, not `@[implemented_by]`, because `implemented_by` is trusted and unchecked, while here the equality is a theorem and no proved definition or statement changed (`Step.lean`, `Truth.lean`, `Status.lean`, `Honesty.lean` are untouched). Profile: 99% of a worst-case `step` is `fallbackMove` (23 ms; `invCount` and `freeKeys` recompute `movable s r` inside the closure they filter with, once per element, and `worstCount` recounts all inversions); `rowLine` runs `decideMove` once per row (844 ms for 36 rows); `State.gate` (76 us) and `rowVerdict` (80 us) recompute `r.pinBehind`/`r.pinOpen` per key. Two fixes: (1) the inversion count after dragging `k` is `invs M + cost i`, where `M` is the movable record keys without `k` and `i` the place the drag takes `k` to; one scan (`costScan`) gives `cost i` for every `i`, each candidate is scored once (`argminV`), and the penalty is two counts computed once (`afterCount_eq`, `fallbackMoveF_eq`); a read that lists a key twice takes the specification's own code, so nothing restricts the inputs; (2) shared lists (`movable`, `pinOpen`, `pinBehind`, the record prefix) are computed once and passed to `@[noinline]` helpers (a `let` used once under a lambda is inlined back by the compiler and recomputed per element). Measured through the Swift `DecisionCore` (`SOMMELIER_PERF=1 swift test --filter PerfTests`, 36-key record, 25-key read, reversed so the anchor rule gives no move): `step` 23.5 ms to 76 us (10 owed keys: 109 us), 36 `rowLine` 844 ms to 2.7 ms (10 owed keys: 4.2 ms), `shownVerdict` 95 to 6 us, 36 `rowVerdict` 2.9 ms to 0.19 ms (the "before" figures are the same Lean code timed natively). `lake exe fastfuzz` compares fast and specification on 10000 random states and reads (36-key records, duplicate keys, owed keys, holds, in-flight drags); the `fast_*` mutants in `scripts/mutants.py` each break a fast definition and must fail an equality theorem.
Size: the app does not depend on `DecisionCore` until ejb.7, so the shipped binary is unchanged today. With a temporary link (a throwaway reference from `Sommelier`, reverted) the release binary grew by 2.44 MB (7,188,168 to 9,751,864 bytes); the static library is 17 MB before dead-stripping.
